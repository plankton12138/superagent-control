# 002 授权（Authorization）

> 本文为中文译本，内容以英文原文为准：[原文](002-authorization.md)。

授权决定谁可以启动工作，以及该工作可以包含什么。本文建立在[001 领域模型](001-domain.zh-CN.md)之上。

宿主执行允许列表、规则和授权。消息、评论和引用的文档是决定的输入；它们不能更改这些权限。

## 触发的两条路径

### 评估：决定是否启动工作

来源会记录消息是否指向智能体：提及机器人或智能体账号记为 `mention`，私信记为 `direct`。准入检查发送者和来源的策略：

- 允许列表上的人若指向智能体，即构成明确请求。
- 人在带有工单的线程上的跟进，遵循下文规则。
- 其他人类消息按其接收范围适用准入表。
- 来源机器人列表上的机器人可以产生推断候选，但绝不能产生明确请求。其他机器人不予准入。

### 订阅：延续既有工作

已订阅线程上的每条消息都会作为上下文到达其订阅的工单，包括来自机器人和 CI 的消息。这种投递绕过准入，且不授予新权限。每个工单仍受其授权限制。

工单自有线程上的人的消息，由该工单的执行器决定。主 Session 把消息附加到工单时也是如此。执行器拥有该消息期间，消息不经过评估，也不会得到决定。每个执行器要么在其工单范围内处理该请求，要么将其交回以便在别处路由。

只要工单在途，归属关系就持续存在，即使有人移除了其订阅。它也覆盖未被人员停止、且该消息正等待将其恢复的已结束工单。

主 Session 会收到跟进通知。执行器拥有该消息期间，主 Session 只能应此人之请求停止工作；接单、附加、忽略和重新排队都会被拒绝。停止仍会带着下文所述的跟进强度通过准入。

### 交回与释放跟进

当一条消息请求的工作超出工单范围或属于另一个工单时，执行器会将其交回一次。工单保留其订阅。若附加的线程无关，执行器会交回其在其中拥有的消息。

只有在不再有任何工单拥有某条消息之后，它才会进入新一轮评估。其候选会包含各执行器的理由。准入把它当作该线程上的普通消息来判断，主 Session 可以接单、附加到别处或忽略。交回一个工单本不拥有的消息（例如机器人消息或人已送往评估的消息）不会排队任何内容。

工单结束时，会释放其执行器未读取或未接手的跟进。这包括从未投递给执行器的消息，以及在其最后一份报告或回合结束之后投递的消息，前提是执行器既未确认、未答复，也未交回它们。当没有其他工单拥有时，每个被释放的消息都会进入评估。停止只结束被停止工单的工作。

被停止的工单不会把它的停止消息再次送往评估，除非另一个工单将其交回。执行停止的主 Session 可以把该消息的其余部分作为新工作接单。

人可以从面板把已被拥有的跟进送往评估。若主 Session 之后又将其附加回在途工单，执行器会再次收到它。当没有任何有效判断覆盖该消息时，面板也会提供重新评估。

### 仅作上下文的订阅

执行器可以为获取上下文而关注相关线程，例如另一个 Issue 或 PR。其消息会到达工单，但不授予权限或跟进强度。除非主 Session 附加来自该线程的消息，否则其中的人的消息不会恢复已结束工单。主 Session 关于其他工作的说明也仅是上下文。

未到达任何工单的人类消息都走评估路径，包括其工单已被人停止的线程。机器人消息无论是否投递到已订阅工单，都会走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit | 允许列表上的人指向智能体，或在已有工单的线程上跟进；准入表中设为明确请求的单元格 |
| inferred | 不在列表上的人在带有工单的线程上跟进，除非其准入表单元格为明确；准入表中设为推断候选的单元格；来源机器人列表上的机器人消息，且指向智能体或到达来源接收所有消息的位置 |
| not admitted | 其他机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的所有推断情形 |

对未列入允许列表的人，明确准入单元格优先，即使在带有工单的线程上也是如此，并且在任何接单模式下都有效。否则其跟进属于推断，在 `off` 模式下不予准入。仅因上下文而关注的线程上的消息使用准入表，而不使用跟进强度。

## 准入

每个来源的策略都有一张准入表。其行是接收范围：

- **飞书：** 每个已配置的群、机器人收到提及的其他群，以及私信。其他群仅在飞书卡片上把 **其他群** 设为 **仅 @** 时才接收。
- **GitHub：** 新 Issue、新 PR、评论和默认分支的 CI。

每行最多有三个单元格。每个单元格决定消息成为明确请求、推断候选还是什么都不是：

| 单元格 | 可选值 | 默认值 |
| --- | --- | --- |
| 在列表上，未指向智能体 | inferred, ignore | inferred |
| 不在列表上，指向智能体 | explicit, inferred, ignore | ignore |
| 不在列表上，未指向智能体 | inferred, ignore | ignore |

未指向智能体消息的单元格仅在来源接收所有消息时可用，例如设为 **全部消息** 的飞书群，或启用了接收全部开关的 GitHub 范围。CI 结果没有发送者，因此其行只提供最后一个单元格。机器人消息使用机器人列表，而不用这些单元格。

把“不在列表上且指向智能体”的单元格设为 explicit，可让该范围内的任何人通过提及智能体来请求工作。这对专门的支持群可能有用。推断候选仍取决于接单模式。跟进通常绕过此表，但明确单元格仍会授予明确强度。

准入表是策略版本的一部分。削弱某个单元格不会立即停止依据它接单的在途工单。当这些工单在恢复前重新校验时，可能撤销其授权。

### 机器人与自动评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名和飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，其消息可以成为推断候选。它们必须要么指向智能体，要么在接收所有消息的范围内发帖。它们不能发出明确请求，也不能停止工单。

使用普通账号的自动评审者对宿主来说算作人。其评论会到达已订阅工单并产生跟进通知。团队提示词文本必须把这类账号标识为自动评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接单、附加、停止或忽略决定。每一项独立处理：某项被拒绝或缺少字段不会阻止其他项执行。

推断候选通常需要完整研判。有一种捷径：若其卡片明显不涉及任何已启用规则，例如普通闲聊或无关讨论，主 Session 可以直接忽略它。决定会记录 `ignoredFromCard`，以区别于规则研判。主 Session 在其策略提示词部分读取已启用的规则。

接单推断候选始终需要研判。直接接单会拒绝准入未视为明确的触发。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断内容都不会成为候选，例如未指向智能体的消息、机器人消息或不在列表上的人的跟进 |
| `observe`（默认） | 推断候选会被研判；肯定性研判记录为带“would accept”（本会接单）标记的忽略，且不接单任何内容 |
| `auto` | 推断候选的肯定性研判会接单该候选 |

明确请求在任何模式下都有效。从 `observe` 开始，在审阅已记录的决定后再切换到 `auto`。每次研判都会对每条已启用规则恰好判断一次，无论是否匹配。主动接单至少需要一条匹配的规则。

每条规则描述一类主动工作。工单的授权会记录匹配的规则，其执行器会收到这些规则的名称和指示。

对该工单而言，规则的流程与沟通要求会覆盖默认值。静默规则可以抑制确认；评审规则可以指定所需评审者及合并前审批。适用于所有工单的要求则属于团队提示词部分。

## 策略版本

规则、接单模式和每个来源的策略共同构成策略版本。每个授权都会记录其接单时所用的版本。

版本变更会丢弃正在运行的评估，并重新排队其触发。它还会向每个受影响的在途工单发送一条策略变更输入。该输入说明是否：

- 某条匹配规则发生了变化（包括其新文本），或不再适用；
- 请求者不再可以启动工作；或
- 主动工作不再被接单，例如模式已从 `auto` 变更。

未受影响的工单不会收到通知。变更不会立即撤销在途工单的授权。

来源配置与策略分离。它控制进入系统的内容：读取哪些群，以及某个范围接收所有消息还是仅接收提及。授权会记录其来源和接收范围。恢复需要来源仍监听该线程，但不要求它仍接收该处所有消息。

来源关闭期间，回复会等待。若来源不再监听其目标位置，回复会被丢弃。

关于执行器可以用自身结果做什么的条件（例如何时可以合并）并不决定谁可以授权工作。它属于智能体的指示，而不属于策略。

## 恢复与停止

已结束的工单保留其授权。人在其自有线程之一上的消息可以恢复同一工作，无需新的评估或决定，无论发送者是谁。机器人和 CI 不会唤醒已结束工单。执行器决定该请求是否符合范围，若不符合则结束本轮。

只有三种操作会改变授权：接单创建它，人的停止撤回它，重新校验失败撤销它。被人停止的工单保持结束状态，不再接收任何内容。在那里请求的工作需要新的接单。

### 恢复前的重新校验

来源必须仍在监听原始线程。其余检查取决于授权的依据：

- 明确跟进授权直接通过。
- 推断授权需要 `auto` 模式，且其匹配规则仍处于启用状态。
- 由表格单元格准入的授权，在今天的表格和发送者成员关系下，仍必须至少获得其原始强度。因此，把发送者从列表中移除，可能撤销通过“列表内发送者”单元格接单的授权。
- 机器人授权要求该机器人仍在来源的机器人列表上。推断表格授权和推断机器人授权还需要 `auto` 模式以及已启用的匹配规则。
- 其他授权要求发送者仍在来源的允许列表上。

若重新校验失败，工单保持结束，且不接收任何等待中的消息。每条消息都被视为未到达任何工单；若没有其他工单拥有它，它就进入评估。主 Session 不会被告知它到达过 worker。这也适用于处理暂停之后。附加到该工单的请求会被拒绝，进一步工作需要新的接单。

- **人在线程中说“停止”属于普通触发，** 由评估决定停止。执行器不能宣称有人要求它停止。
- **面板中的停止是命令。** 它直接作用于工单，并记录为人工停止。
- **等待条件属于来源。** 诸如“N 小时无人处理”的条件会是一个自行等待并再次检查的来源；评估从不等待。

## 评估未完成时

时限从候选到达主 Session 时开始。等待投递所花的时间不计入，未投递的候选永不超时。

超时的评估会把其触发排队以便再次尝试。连续两次重试之后，第三次超时会记录 `unavailable`。研判失败也会记录 `unavailable`；之后的触发可以启动新的评估。策略变更或依据过时策略作出的决定会记录 `unavailable`，并立即按当前版本重新排队该批次。

`evals` 健康条目会报告最近一小时内尚未解决的不可用决定。`scripts/dsh-superagent status` 会包含该错误。

仅当不可用决定距今不足 24 小时、仍是其线程上最新的决定、尚未被忽略，且该线程既未排队也未在评估时，面板才会请求人工关注。人可以再次评估该触发，或忽略该问题。
