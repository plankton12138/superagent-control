# 003 执行（Execution）

> 本文为中文译本，内容以英文原文为准：[原文](003-execution.md)。

本文跟踪一个已接单的工单走过执行、投递与恢复的全程。它建立在[001 领域模型](001-domain.zh-CN.md)和[002 授权](002-authorization.zh-CN.md)之上。

## 工单阶段

每个打开状态的工单只有一个阶段，由其等待的内容决定。自上而下阅读表格；第一个匹配行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，随后延迟翻倍直至一分钟；成功、新的派工或工单结束会清除该状态 | 输入未投递 |
| person / answer | 存在待人工决定事项 | 等待回答 |
| person / review | 最新报告为 `ready` | 等待评审 |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息到达该工单 | 受阻 · 失败 |
| working / queued | 没有派工，或派工处于待启动 | 排队中 |
| idle | 最新报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其他所有情况 | 工作中 |

`person` 阶段表示工单在没有人工输入时无法继续。新的人类消息会把 `blocked` 或 `failed` 工单释放给其执行器，于是它进入下一个匹配阶段，通常是 `working`。

`idle` 工单已结束其回合且没有悬而未决的问题。已订阅线程上的触发可以继续它。

## 执行器

每个工单会得到一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以工单短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以操作者的操作系统用户身份、无需审批地运行命令。其 `dsh-superagent-worker` 预设包含工作所需工具，并在 5 秒后把前台 shell 命令转为后台作业。这样 worker 可以在下一步接收新消息，而不必等待长命令结束。

主 Session 使用 `dsh-superagent-router`，同样有 5 秒的 shell 与作业等待限制，以及更小的路由工具集。Session 会保留创建时选定的预设。worker 子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与 worker 槽位

当回合结束时仍有 shell 作业或子智能体在运行，工单会保留其 worker 槽位并保持工作状态。它不会被报告为等待，主 Session 也不会收到等待报告。已完成的作业或子智能体会在同一槽位中以结果唤醒执行器。一旦回合结束时没有后台工作，执行器就正常报告等待。

每个回合结束后，后台工作最多有 30 分钟完成。达到该时限时，shell 作业会被终止，工单被报告为等待。报告包含执行器的最后话语，以及哪些作业被终止或哪些子智能体仍在活动。子智能体允许继续运行。执行器会在下一回合读取被终止作业的结果。

移交给人工会立即释放槽位，并让报告保持生效。这适用于 `ready` 报告或提问之后（除非此后又有其他输入到达），以及任何 `blocked` 或 `failed` 报告之后。

移交时，子智能体停止。shell 作业（例如为评审提供的服务器）可以继续运行直到派工结束。它们不占用槽位，也不受 30 分钟限制约束，包括在后续回合之后。它们完成时不会唤醒执行器；执行器会在下一回合读取结果。

人也可以直接在执行器 Session 中写入来启动回合。其后台工作遵循相同规则。

派工结束时，其 shell 作业会被终止且不唤醒 Session。其子智能体会被释放，它们唤醒的任何完成回合都会被丢弃。替代派工及其等待中的输入会在关闭完成后启动。

在 DeepSeek Harness 进程内停止或重启插件会走相同的关闭路径。尚未纳入 Session 历史的输入会被保留。关闭会为每个 worker 的后台工作最多等待 10 秒；进程重启则会直接终结该工作。忙碌时被中断的派工会带着恢复说明重新开始。

worker 子智能体（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并采用 worker 的权限。它们只保留 worker 允许的工作工具，并在工单结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子智能体结束时，其作业会被终止。

### 准备工单目录

在首次派工之前，如果工单目录不存在，准备命令会在执行根目录中以 `sh` 运行一次。它有十分钟完成。若没有准备命令，worker 会在空目录中启动。

命令失败会使工单失败，并记录其输出。重试或人在工单某个线程上的消息会再次尝试准备。典型命令使用 `git worktree` 创建检出。当 PR 分支的最后一个路径段与工单短名匹配时，该 PR 属于该工单。

### 并发

工单从启动开始时（包括准备阶段）就持有一个 worker 槽位，或从唤醒其空闲执行器的投递开始持有。它在活跃回合期间也始终持有该槽位。

配置的并发上限作用于这些槽位，并为人消息或状态请求额外保留一个槽位。当普通槽位已满时，此类唤醒可以使用额外槽位，并在新启动之前占用下一个空位。因此，新工作无法阻止人继续既有工单。

其他输入（例如 CI 结果）会等待普通槽位。启动会在 `working / queued` 中等待，直到有槽位空出。启动并发运行，因此缓慢的准备命令只会拖延它自己的工单。

### 执行变量

准备命令和执行器指示会收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取它们的值和说明。这些变量都不包含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监视的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或 PR，以及当其为 PR 时的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动该工单的群聊 |

工单专属的值来自其目录和原始触发。其他值来自当前部署设置。只有面板可以更改执行环境设置；发送给主 Session 的文本无法更改已配置的 shell 命令。

worker 通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被阻止的命令按名称调用时会失败。

这些包装器和目录建立的是默认值，而非安全边界。worker 仍可通过绝对路径执行程序。

## 合并

自动合并由**交付要求**（Delivery requirements）提示词管理。宿主没有针对合并的专用决定逻辑。

默认情况下，执行器绝不使用智能体账号启用自动合并：GitHub 会把合并归因于启用它的人。交付要求必须指定另一个账号的 CLI 用于合并。若没有指定，则由人合并 PR。

默认指示仅允许对为该工单开启的 PR 自动合并，且需满足：它已就绪、所需审批覆盖 head commit、新增与删除总计少于 200 行。在推送另一个修订之前，执行器会撤回自动合并。

没有正文的评审（例如批准）也会作为触发到达，并能唤醒等待评审的执行器。这些指示约束智能体，而非 GitHub 的合并规则。若要强制审批，需在分支保护中要求审批并废弃过期批准。省略合并 CLI 或删除自动合并段落，即可要求人工合并。

## 工单如何结束

- **就绪但无 PR：** `ready` 报告会使工单以已完成状态结束。
- **无事可做：** 执行器若发现没有需要人处理的工作（例如无法复现或已被取代的请求），会报告 `dropped`。工单会结束且不发消息，除非有匹配规则要求发消息；人此后在其线程上的消息会恢复它。
### PR

一旦其执行器报告，工单就会关注它起始所在的 PR。它也会关注从其分支开启的每个 PR（在由执行器报告或由 GitHub 来源发现之后）。重新打开的 PR 会被再次关注。

当它开启的 PR 均不再打开时，工单即完成。若它没有开启任何 PR，则其关注的所有 PR 都必须已关闭。随后它以最后一次相关关闭的结果结束，并保留其订阅，允许之后的人类评论恢复它。

当恢复、重试或恢复执行的工作尚未完成时，关闭不会结束工单。若执行器确认或答复了其拥有的跟进，但此后尚未作出非进展报告，也未在读取该消息后结束回合，工单同样会等待。一旦满足同一 PR 完成规则，之后的 `ready` 报告就会结束工单。

聊天渠道会收到一条关于 PR 结果的最终通知。GitHub 本身就会在 PR 上显示结果。移除工单对某个 PR 的订阅，也会使它停止关注该 PR。

因此，“等待评审”意味着带 PR 的 `ready` 报告。

### 跟进与上下文线程

执行器决定其工单自有线程上的人类跟进。它处理范围内的请求，并交回超出其范围或属于另一工单的请求。一旦没有执行器拥有该消息，它就成为主 Session 的候选。除此之外，主 Session 只能应此人之请求，对该跟进采取停止工作的操作。

输入在 Session 将其纳入某个步骤、并且随后报告或结束回合之后，才算已读。工单结束时，未读且未被确认、答复或交回的消息会返回评估，如[002 授权](002-authorization.zh-CN.md)所述。已读但未采取行动的消息（例如感谢）不会返回。

仅为上下文而关注的线程仍会投递消息，但不会让工单拥有人类跟进，也不会恢复已结束工单。这些消息可以独立评估。

在有在途工单订阅期间，来源会轮询已订阅线程；在最后触发与订阅工单结束两者之中较晚者之后，还会持续两周。此后，消息仅通过常规入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、发生错误（记录为 `failed`）时，工单不接收任何自动输入。

模型提供方或网络的暂时性失败（HTTP 408、429 或 5xx，或连接被拒绝、重置或超时）会先重试三次，退避时间递增：启动会再次运行，回合失败的 worker 会被告知继续；失败的准备命令不会重试。

一旦失败，CI 和机器人消息会被记录在该工单上，但不会投递，也不会唤醒 Session。

其工具仍可用，因此人可以直接在该 Session 中继续。

失败的启动不会自行重试。

人的消息、此后既非 `blocked` 也非 `failed` 的报告，或一次重试，都会结束该保持状态。

该状态由已存储的报告和输入推导得出，因此重启后仍会保留。
### 重试

当打开状态的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：为每种情况提供的补救办法都是新建派工，它会重新启动其 worker 并接收等待中的输入。

一旦人的消息到达受阻或失败的工单，执行器就拥有该消息，因此工单显示为工作中；若失败的启动重新开始，则显示为排队中；且不再提供重试，除非投递该消息失败。

重试会结束当前派工，并在同一执行器 Session、目录、分支和 PR 中启动新的派工。

执行器模型只在创建 Session 时生效；既有 Session 保留其模型。
### 重启

运行中的派工会以“host restarted”结束，新派工则以恢复说明启动，指示执行器在重复任何对外操作之前检查其目录、git 历史和 GitHub，最旧的工单优先。

处于等待、就绪、受阻或失败状态的派工保持原样，除非在该报告之后有输入到达，此时它们也会重新启动。

Session、目录、订阅、待处理消息以及下文所述的已存储工作都能在重启后保留；每个执行器 Session 把哪些消息纳入其历史的记录也会保留。一个步骤在认领消息之后、调用模型之前完成该记录：被重启中断的回合所取走的消息，在随后出现报告或回合结束后计为已读；而某步骤已认领、但在写入历史前被取消或错误中断的消息，计为未读。

重试或重启会把投递给被替代派工、但其执行器 Session 未取走的消息（可能因取消或步骤中断而丢失）再次交给新派工；仍在该 Session 中等待的副本（由重启保留或跨崩溃持久化）会在新派工的第一条消息之前被取出，因此新投递是唯一的副本。
### 已存储的工作

dsh-superagent 在作出决定之后要做的事，例如把候选、跟进或报告转达给主 Session、启动派工或投递输入，都会先被存储，然后再执行。

失败的转达或投递（例如无法联系其 Session）会在 2 秒后重试，随后延迟翻倍直至一分钟；失败的启动会使工单失败，除非该失败如上所述属于暂时性失败。

每种工作在某一项连续失败三次之后，才会在总览的系统问题中报告错误；失败的输入投递则显示在其工单上。

发往主 Session 的转达保持顺序，通知也是如此；某项失败会阻塞其同类后续项。
### 来源失败

GitHub 来源会分别读取每个 Issue、PR 和线程：失败的读取会把错误保留在其线程上，在下次轮询时再次读取，并计入来源错误数；默认在连续三次轮询失败后报告该错误；任何成功的轮询都会重置计数。

当智能体失去对私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会重试。

已收到通知、但读取持续失败的 Issue 或 PR，会在首次读取失败一天后被丢弃；若 GitHub 报告其已删除，则立即丢弃。此后它不再使轮询失败，其线程保留该错误，来源状态会列出它。

其读取位置保持不变，因此之后的某项通知或对其线程的轮询会读取失败读取所遗漏的内容。

飞书事件消费器会报告每次失败，对已订阅主题的轮询会把每次失败保留在其线程上。

GitHub 列表或飞书页面中格式错误的项会被跳过，来源状态会将其计入。
### 渠道失败

外发消息会作为已存储工作保存并发送，以 5 秒起的退避重试，翻倍直至 300。

工单发往同一会话的消息按排队顺序发出，因此其确认先于之后的答复或结果：同一工单发往同一会话的较早消息尚未发出时，后续消息会等待，直到该较早消息连续失败三次并显示为问题。

其他工单的消息，以及不属于任何工单的消息，不会等待它。

有失败尝试的消息在发出或被撤回之前，都算系统问题。

只有当其来源不再监听该会话，或来源答复该会话永远无法接收时，消息才会被丢弃；来源关闭期间，它会等待。

对于已删除的 Issue、GitHub 上被锁定的会话、被撤回的消息，以及飞书上已找不到的消息，来源会作出这种答复。

对已不存在的评审评论的回复，会改发到 PR 的会话中。

被丢弃的消息保留其记录，包括丢弃时间、原因和所属工单，因此它永远不会再次排队；被丢弃的确认显示为已丢弃，而非已发送。
### 暂停处理

停止派发、新的评估、评估超时、输入投递和回复；已在进行的启动会等到处理恢复。

来源继续记录触发，运行中的执行器回合不会被打断。

人发给已结束工单的消息会等待：暂停后的第一轮处理会在该工单的授权在当时策略下仍然成立时恢复该工单。

进行中的评估在暂停期间不会超时；其截止时间会按暂停时长顺延。
### 无效配置

被其类型拒绝的已存储来源配置会禁用该来源实例。
